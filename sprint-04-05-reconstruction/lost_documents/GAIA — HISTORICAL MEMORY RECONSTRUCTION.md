Do not treat recommendation as authorization

23. Lessons learned
Architectural lessons
1. Boundaries must be explicit

Historical trigger: Toolkit and Local Engineer evolution.

The project repeatedly learned that a useful capability can still be architecturally dangerous if its scope is implicit.

2. Evidence does not automatically become architecture

Historical trigger: host validation, HA discovery and implementation reviews.

The project increasingly treats implementation evidence as evidence, not permission to redesign.

3. Frozen means frozen

Historical trigger: Toolkit V0.1.

A later capability must not be smuggled into an accepted/frozen boundary.

Engineering lessons
4. Real hosts expose assumptions

Historical trigger: 3090 → 1070 validation.

Local engineering can hide environmental assumptions that only appear on the target host.

5. Bounded primitives are easier to reason about

Historical trigger: validation modularization and Local Engineer discovery.

Small operations with explicit limits provide more useful evidence than an unrestricted "do whatever is necessary" capability.

Validation lessons
6. A green operation is not a correct conclusion

The strongest formulation in the current project is:

operation_success
    ≠
evidence_sufficiency
    ≠
semantic_correctness

This is a direct historical culmination of repeated validation problems.

7. Blocking must be dependency-aware

A failed operation is not necessarily a globally blocking failure.

Evidence lessons
8. Provenance is part of evidence

Evidence without:

source
operation
round
baseline/context

is difficult to interpret or reproduce.

9. Truncated evidence must remain explicitly truncated

A bounded result cannot silently be presented as complete evidence.

Git lessons
10. The authoritative checkout matters

The current implementation process repeatedly distinguishes Engineer workspaces/packages from the Human Owner's authoritative checkout.

11. Branch state must be explicit

The available record repeatedly emphasizes checking branch state before commit/push.

Documentation lessons
12. Repository structure does not create authority

Folder placement is classification, not architectural acceptance.

33. Historical interpretation

BUILD SOMETHING
      ↓

      ↓
DISCOVER THAT "WORKED" IS NOT ENOUGH
      ↓

      ↓
DISCOVER THAT EVIDENCE NEEDS PROVENANCE
      ↓
DISCOVER THAT EVIDENCE DOES NOT EQUAL AUTHORIZATION
      ↓
MAKE BOUNDARIES EXPLICIT
      ↓
FREEZE SUCCESSFUL BOUNDARIES
      ↓
ADD NEW CAPABILITIES OUTSIDE THOSE BOUNDARIES
      ↓
CLASSIFY KNOWLEDGE AND AUTHORITY

That explains why the later GAIA state is considerably more conservative than a simple progression from "prototype" to "agent platform."

The historical memory is therefore not merely:

GAIA built increasingly sophisticated components.

It is also:

GAIA repeatedly discovered that scope, evidence, authority, provenance and validation semantics had to become more explicit before additional capability could safely be generalized.
